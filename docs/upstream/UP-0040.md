## UP-0040 — a run with a tweaked config never gets a backup (`OURS`)

Found on 2026-11-13 while deciding what "a run started from reviewed code" requires for run-log upload (an
allowlist; `docs/upstream/UP-0038.md` lists the slice's other open items). The rule adopted, on Fable's advice:

- the run's commit is on `origin/master`'s history, checked at upload. A clean run from an unpushed commit uploads
  once that commit is pushed, unless a rebase or squash means its sha never lands;
- nothing the entry point loads, and no file under `configs/`, had local edits, was untracked or was ignored when
  the run started (`entry_modified`, written at start). Such a run never uploads.

Why configs cannot simply be exempted (Fable, verified in code): `opengrad evaluate` names no config in its
command, but reads suite and benchmark configs by name (`src/opengrad/cli.py`, `src/opengrad/benchmarks/runner.py`),
and the marker check reads only configs named in the arguments. `opengrad train` reads whatever its config points
at, including an absolute `preference_path` and a `release_dir` with no containment check, so a renamed copy of
held-out data would pass a name check.

Cost: ordinary work, tweaking a config just before a run, leaves that run's log with no backup. It stays on the
machine, listed as not approved.

Refinement, done 2026-11-13:

- At run start, `inputs.consumed_configs` lists the configs the run consumes: every `configs/` file its arguments
  name and, for `opengrad evaluate`, the suite file (`--suite`, default `smoke`) and each benchmark config the suite
  lists, resolved as `opengrad.benchmarks.runner` does. A benchmark the runner would load from outside
  `configs/benchmarks/`, or a suite that cannot be read, makes the answer unknown, and the run never uploads.
- `config_blobs` records the git blob id of each, from the bytes the run read (what `git hash-object` prints).
  These configs are left out of `entry_modified`; any other `configs/` edit still counts there and blocks.
- At upload, `scripts.configs_pushed` requires each blob to appear at that same path in `origin/master`'s history
  (`git log --raw`, with literal pathspecs). A version pushed earlier counts, since it was reviewed when pushed. A
  version that only a merge commit introduced is not seen, which fails closed.
- Getting the consumed set wrong is safe in one direction only, by design. A config the run reads but the list
  misses stays under the old rule, so an edit to it still blocks.
- An unrelated stray file under `configs/` still blocks every approved upload. Narrowing that needs to know
  everything a config itself points at (`opengrad train` follows paths inside it), so it stays strict.
- Tests: `tests/runrecords/test_upload_hardening.py` (`test_a_tweaked_config_uploads_once_that_exact_version_is_pushed`
  and its neighbours).

Also open, from the same audits:

- **Modal runs.** `scripts/modal/*` copy only `src/opengrad`, with no `.git`. Since 2026-11-13 each launch records
  itself locally (`_record_launch`; no Modal run has exercised it yet), with the launching checkout's commit and
  `entry_modified`. No Modal launcher is approved for upload. Approving one would also need the shipped source
  anchored: today `entry_modified` watches only what the launcher itself loads, not the whole `src/opengrad`
  tree that `gguf_study.py` ships.
- **Arguments and the local ref.**
  - `unchecked_inputs` flags any existing file outside `configs/`, including an output file a re-run overwrites.
    That fails closed, but it is noisy.
  - Directory arguments are not checked at all.
  - Ancestry trusts this checkout's `refs/remotes/origin/master` (by its full name, so a local branch or tag
    called `origin/master` does not count). That guards against accidents, not against someone editing the ref.
