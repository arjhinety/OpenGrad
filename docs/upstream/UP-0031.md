## UP-0031 — escape sequences mangled by shell-quoted edit scripts (`OURS`)

On 2026-11-11, several file edits were made by Python snippets passed to the shell, as a quoted heredoc or as
`python -c "…"`. Escape sequences did not survive the extra layer of quoting:
- A replacement meant to write `\b` in `LATER_LINE` in `scripts/reporting/generate_upstream_log.py` wrote the
  control character 0x08 instead.
  - Ruff reported it (`PLE2510`).
  - `test_a_later_line_for_another_entry_is_rejected` failed, because the regex no longer matched.
  - Both happened before the commit.
- Two other edits did not apply at all, because the quoting changed their search text, so it no longer matched:
  - the docstring usage line in `scripts/publish_card_corrections.py`, where an earlier quoted edit had itself
    written a literal backslash-n;
  - `render()` in the generator.

  Each time an `assert` stopped the edit script. In the first case the same shell call then went on to its next
  command and appended a new test, and that test reached the real Hub (UP-0030).

Fix: the regex was corrected from a script file (the byte check now shows a literal backslash and `b`). Edits whose
text contains backslashes are now written to a file and run, or made with an exact-replacement editor, never
passed through shell quoting. Lessons:
- After an edit script stops partway, read the whole diff before running anything else (UP-0030).
- Ruff and the targeted tests caught this one before commit; keep running both on every changed file.
