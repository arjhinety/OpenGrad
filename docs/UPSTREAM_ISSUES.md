# Upstream issues log

Every problem OpenGrad hits is recorded here with whose problem it is, so that the ones that really belong to a
library or tool can later go upstream as an issue or a pull request. Started 2026-10-03 at the owner's request.

**Rules**
- **`OURS`**: our code, configuration or usage is wrong. Most problems are this. Recorded so the pattern is
  visible, and so nobody files it upstream by mistake.
- **`UPSTREAM`**: the fault is in a library or tool. It needs evidence before it gets this label:
  - a minimal reproduction outside OpenGrad's code;
  - the exact version;
  - a search of the upstream tracker for an existing issue.
- **`UNCLEAR`**: not yet reproduced in isolation. It stays here until it is.
- **`NOT A BUG`**: documented upstream behaviour we had to learn. Kept so the lesson is not relearned.
- Nothing is filed upstream without the owner's word. A filed issue or PR gets its link in the entry.
- An entry is added in the same commit as the fix or workaround. Entries are not rewritten; a later line records
  what changed (reproduced, filed, fixed upstream).
- **`FEATURE GAP`**: the library or tool works as documented, but lacks something we had to build around, and
  that it could reasonably offer itself. It names the library, the version and our workaround (the file or
  mechanism), so the gap can later become a feature request or a pull request.
- **Upstream status** is separate from the class. The class says whose problem it is; the status says where it
  stands with the upstream project:
  - `not-applicable`: nothing to take upstream (most `OURS` and `NOT A BUG` entries);
  - `not-filed`: may belong upstream, but is not ready;
  - `candidate`: ready to file, with a minimal reproduction and a search of the upstream tracker recorded;
  - `filed`, `merged` or `declined`: with the link.

**How an entry is added**
- Create `docs/upstream/UP-NNNN.md` with the next number. The file starts with a front matter block:
  - always: `id`, `date`, `where`, `class`, `summary`, `state` and `upstream.status`;
  - `UPSTREAM` and `FEATURE GAP`: also `library` and `version`;
  - `FEATURE GAP`: also `workaround`;
  - `candidate` or later: also `upstream.reproduction` and `upstream.tracker_search`;
  - `filed` or later: also `upstream.url`.

  The body follows it, starting with the heading `## UP-NNNN — <title>` followed by the class in backticks and
  parentheses, as in the entries below.
- Run `python scripts/reporting/generate_upstream_log.py`. It rebuilds everything between the generated markers
  from the entry files. `tests/repo/test_upstream_log.py` fails CI if this file is stale or an entry is
  invalid.
- A later line goes at the end of its own entry's file; the check rejects a later line in another entry.

## UP-0001 — a test needed a library CI does not install (`OURS`)

`tests/verification/test_flag_set.py` imported `huggingface_hub.errors` at test time. CI runs
`uv sync --locked --extra dev`, and the dev extra does not include `huggingface_hub`, so CI would have failed. Found by the
independent audit before push. Fix: the test that needs the library uses `pytest.importorskip`, and the rest no
longer need it. Lesson: a test may only import what the dev extra installs.

## UP-0002 — case-colliding fixture names (`OURS`)

Two fixtures named `c0-s0.yaml` and `C0-s0.yaml` coexisted on Windows, where the filesystem is case-insensitive,
and broke on Linux CI. Fixed by renaming (37088b6). Lesson: never let two paths differ only by case.
- **Correction (audit, 2026-10-03):** they did not coexist on Windows. There the second file overwrote the first;
  only Linux held both.

## UP-0003 — pyarrow has no type information (`UNCLEAR`)

`import pyarrow.parquet as pq` under `mypy` strict (mypy 2.3.1) reports `import-untyped`, because pyarrow 25.0.1
ships no `py.typed` marker (checked: no `pyarrow/py.typed` in the installed package). Worked around per import.
- **Before filing:** search the apache/arrow tracker for an existing typing or `py.typed` issue, and check
  whether a community `pyarrow-stubs` package already covers this.
- **Likely outcome:** a known upstream limitation, in which case add a link here rather than filing.

## UP-0005 — a cache miss is a `FileNotFoundError` (`NOT A BUG`)

In huggingface_hub 1.29.0, `LocalEntryNotFoundError` subclasses `FileNotFoundError` (its method resolution order is
`LocalEntryNotFoundError, FileNotFoundError, OSError, EntryNotFoundError`). Catching `FileNotFoundError` to mean
"the dataset is not cached" therefore also caught real failures such as a deleted pinned manifest, and reported
them as a missing input. `flag_set._input_missing` now matches only the cache miss and missing modules.
- **Correction (audit, 2026-10-03):** "documented" overstates it. The subclassing is visible in the class
  hierarchy; the exception's docstring does not mention `FileNotFoundError`.

`configs/annotation/first-reply-review-v1.rubric.md` described a decline with a phrase the publication-hygiene

## UP-0009 — a report checked the flag set against itself (`OURS`)

`flag_triage_report.report` passed `set(source_of)` as the flag set's members, but `source_of` is built from the
triage population, the very thing the check is meant to compare with the flag set. The check could never fail.
The result was still right, because the population equals the flag set, but nothing re-read the members file.
Found by the independent audit before push. The report now reads the hash-checked members file and the
populations manifest's `members_sha256`. Lesson: a check must take its expected value from an independent source.

## UP-0010 — populations that could not come back (`OURS`)

The triage populations (17.7 MB) may be left uncommitted, but `verify()` raised `FileNotFoundError` when they
were absent, and `write()` refused to recreate them once the manifest existed. Found by the audit. Fixed: absent
files report `BLOCKED_INPUT_MISSING`, and `--restore` rebuilds them from the pinned release, writing only if the
rebuild reproduces the committed manifest exactly. The first version of `--restore` wrote one file before
finding the other differed, so a refusal could leave a half-restored directory; its own test caught that before
commit, and it now checks both before writing either.

## UP-0011 — the validator crashes on a malformed reference file (`OURS`)

An unquoted value containing ": " made `docs/references/papers.yaml` invalid YAML. `opengrad-validate` then died
with a PyYAML `ScannerError` traceback from `validators._paper_ids`, which loads the file a second time outside
`check_references`' own load-error handling, instead of reporting a validation error. PyYAML's behaviour is
correct (`NOT A BUG` on its side). The broken file reached a local commit because the check and the commit were
chained with `;` rather than `&&`; it was fixed and amended before any push. Lessons: chain a commit after its
checks with `&&`; `_paper_ids` should reuse the reported load error.
- **Again, 2026-10-04:** a check piped into `tail` (`pytest ... | tail -1 && git commit`) let a failing index test
  through, because a pipeline's exit status is the last command's; and a later commit was gated on its tests but
  not on the hygiene scan, which had flagged a home-folder-style path in a new test. Both were caught at once and
  amended before any push. Capture each check's exit code before filtering its output, and gate on every check.

## UP-0014 — regression checks that skip silently (`OURS`)

The non-regression loop that `tool_use_promotion_v5` and v6 inherit (`PromotionPolicyV2.evaluate`) checks call
precision, call recall, clarification accuracy and unsupported accuracy only when both the candidate and the baseline
carry the metric. v6 requires from the baseline only `call_f1` and `answer_rate` (`V6_BASELINE_METRICS`), and the
gate the same (`BASELINE_METRICS`); v6 alone also does not require call precision or call recall from the candidate.
A baseline without one of the four passes that check by skipping it. v6's comment says it does not fill in absent
metrics the way v5 did, so this looks unintended. Found by the Opus review of the formulas draft, confirmed in the
code. Not fixed: the policy is preregistered, and changing what it requires is the owner's decision.

Later line for UP-0014, 2026-10-13: closed for the gate by contract 4, which requires the four metrics in the
baseline. `tool_use_promotion_v6` used on its own still skips them. The "owner's decision" above concerned changing
what the policy requires; the gate now refuses a baseline without them and the policy is unchanged, on the basis
ERRATA §35 states (02 H5, 07's policy column, §19).

## UP-0015 — errors in the formulas draft, caught by review (`OURS`)

`EVALUATION-FORMULAS-DRAFT.md` (8ff3c8e, cbcd437) was reviewed by Codex and an Opus subagent before any push.
- Open question 3 doubled the resolvable margin for a paired difference. The existing margin already equals a paired
  difference's worst-case half-width; doubling is a second reading, which the draft had not called a reading.
- It said comparisons are made at 9 decimal places; the policy uses 6.
- It said check 14 applies the margin to paired differences; the code does not know.
- It said the answer and refusal instrument was not built; 46 names the frozen classifier v2.
- It said its test recomputes every number; some were read from the trial report.

One reviewer finding was itself wrong: `CALL.on_ambiguous_in_M` is a `CALL` row, not a global one. Lesson: a draft that
restates rules gets its numbers and its readings checked against the code, and every reviewer finding is checked
too before it is relayed.

Later, 2026-10-06: the pre-push audit of 7e97306 found one more. The draft called condition 1's margin "two readings"
(10 points, or $M(n)$), but 06 says 11 "fixes that margin" and "no claim in this study uses a margin below 10pp": the
margin is 10 points and $M(n)$ is a further requirement. Fixed in the draft; the test now checks each quoted passage
against its source document.

## UP-0036 — the scanner's home-path pattern backtracked exponentially (`OURS`)

Found on 2026-11-11 while timing the run-record redactor. The drive branch of `HOME_PATH` read
`[A-Za-z]:(?:\\\\|\\|/)+Users`. One alternative is two backslashes, another is one, so a run of n backslashes can be
split into one- and two-backslash pieces in a Fibonacci number of ways. With no `Users` after the run, the engine
tried each split: 28 backslashes after `C:` took about 0.05 s, each further backslash multiplied that by about
1.6, and a few hundred did not finish within two minutes. The upload check searches every log with it and the
redactor applies it to command arguments and error messages, so one odd log could hang an upload. The scanner
runs it on data files and archive members, so one such file could hang CI.

Fix: the repeated group is now the character class `[\\/]+`. It matches exactly the same strings, one or more
backslashes or slashes, but each character can be taken only one way. The two copies stay byte-identical (a test
checks that). Every count in the scan was unchanged, and the scan still passes. A test now requires
`HOME_PATH.search` to finish within 1 s on 40 backslashes after a drive letter (the old form took about 18 s, so
the test fails rather than hangs), and on 5,000 slashes.

Lesson: in a repeated group, no two alternatives may match the same text. Write a separator run as a character
class, never as an alternation of its lengths.

## UP-0039 — agy 1.5.8 reads files with a tool the gate did not allow (`UPSTREAM`)

Found on 2026-11-13 when Gemini 4 Argon was consulted through agy under the tool gate (INC-0002). Its four attempts
to read its input were all denied, and it answered that it could not read the file. The gate allowed exactly one
tool, `view_file` with the argument `AbsolutePath` (UP-0012). The installed agy reads files with `read_file`, whose

Effect: the gate failed closed. Nothing outside the input was read. But a labelling run with this agy version
would read nothing, and the runner would record no labels, since it requires the gate to have allowed a read.
A hook that fails to start: three forms were probed with an input holding a word the model could not guess, and
each blocked the read (the word never appeared): a hook pointing at a missing script; the whole command in one pair
of quotes; and the runner's own form for a path containing a space, an extra outer pair of quotes around quoted
parts. Only these three were measured, so "a broken hook blocks the read" is shown for them, not for every way a
hook can fail. An earlier probe whose model answered "hello" with no gate log does not show a bypass: its input
said "hello", a word the prompt made easy to guess, which is why later probes used an unguessable one.

of quotes, which made agy's hook fail to start. It failed closed, but a labelling run from such a path would have
read nothing. Each part quoted once works: the gate ran, allowed the read, and the model returned the word.

## UP-0040 — a run with a tweaked config never gets a backup (`OURS`)

Found on 2026-11-13 while deciding what "a run started from reviewed code" requires for run-log upload (an
allowlist; `docs/upstream/UP-0038.md` lists the slice's other open items). The rule adopted, on Fable's advice:

- the run's commit is on `origin/master`'s history, checked at upload. A clean run from an unpushed commit uploads
  once that commit is pushed, unless a rebase or squash means its sha never lands;
- nothing the entry point loads, and no file under `configs/`, had local edits, was untracked or was ignored when
  the run started (`entry_modified`, written at start). Such a run never uploads.

Why configs cannot simply be exempted (Fable, verified in code): `opengrad evaluate` names no config in its
command, but reads suite and benchmark configs by name (`src/opengrad/cli.py`, `src/opengrad/benchmarks/runner.py`),
and the marker check reads only configs named in the arguments. `opengrad train` reads whatever its config points
at, including an absolute `preference_path` and a `release_dir` with no containment check, so a renamed copy of
held-out data would pass a name check.

Cost: ordinary work, tweaking a config just before a run, leaves that run's log with no backup. It stays on the
machine, listed as not approved.

Refinement, done 2026-11-13:

- At run start, `inputs.consumed_configs` lists the configs the run consumes: every `configs/` file its arguments
  name and, for `opengrad evaluate`, the suite file (`--suite`, default `smoke`) and each benchmark config the suite
  lists, resolved as `opengrad.benchmarks.runner` does. A benchmark the runner would load from outside
  `configs/benchmarks/`, or a suite that cannot be read, makes the answer unknown, and the run never uploads.
- `config_blobs` records the git blob id of each, from the bytes the run read (what `git hash-object` prints).
  These configs are left out of `entry_modified`; any other `configs/` edit still counts there and blocks.
- At upload, `scripts.configs_pushed` requires each blob to appear at that same path in `origin/master`'s history
  (`git log --raw`, with literal pathspecs). A version pushed earlier counts, since it was reviewed when pushed. A
  version that only a merge commit introduced is not seen, which fails closed.
- Getting the consumed set wrong is safe in one direction only, by design. A config the run reads but the list
  misses stays under the old rule, so an edit to it still blocks.
- An unrelated stray file under `configs/` still blocks every approved upload. Narrowing that needs to know
  everything a config itself points at (`opengrad train` follows paths inside it), so it stays strict.
- Tests: `tests/runrecords/test_upload_hardening.py` (`test_a_tweaked_config_uploads_once_that_exact_version_is_pushed`
  and its neighbours).

Also open, from the same audits:

- **Modal runs.** `scripts/modal/*` copy only `src/opengrad`, with no `.git`. Since 2026-11-13 each launch records
  itself locally (`_record_launch`; no Modal run has exercised it yet), with the launching checkout's commit and
  `entry_modified`. No Modal launcher is approved for upload. Approving one would also need the shipped source
  anchored: today `entry_modified` watches only what the launcher itself loads, not the whole `src/opengrad`
  tree that `gguf_study.py` ships.
- **Arguments and the local ref.**
  - `unchecked_inputs` flags any existing file outside `configs/`, including an output file a re-run overwrites.
    That fails closed, but it is noisy.
  - Directory arguments are not checked at all.
  - Ancestry trusts this checkout's `refs/remotes/origin/master` (by its full name, so a local branch or tag
    called `origin/master` does not count). That guards against accidents, not against someone editing the ref.
