# OpenGrad evaluation

## Baseline and candidates

- **B0 is immutable.** `opengrad baseline --config configs/evaluation/tool_calling/qwen35_2b_baseline.yaml` runs
  the unmodified pinned model on the frozen held-out set.
  - Use `--dry-run` (CPU deterministic backend) and `--limit N` before spending GPU time.
  - A real run requires readiness `ready_for_baseline` and a PASS GPU boundary receipt
    (`reports/hardware/qwen_gpu_smoke.json`).
  - `run_baseline` refuses any model other than the canonical pinned one. Never relax that guard.
- **Candidates** use the same command with a candidate config (`configs/evaluation/candidates/`) and go through
  `src/opengrad/evaluation/candidate.py`. The candidate path shares `measure_predictions` with the baseline.
  - A candidate may change **only the model**: renderer, template hash, seed, generation, runtime and the
    behavioural manifest are refused.
  - It must record lineage (parent experiment, checkpoint id and step, base model and revision)
    (`docs/CANDIDATE_EVALUATION.md`).
- **Frozen held-out sets:** `reports/evaluation/behavioral-heldout-v2.manifest.json` with its DEV/CONF partition
  `reports/evaluation/behavioral-heldout-v2-partition.json` and quarantine files. Never train on them.
  Readiness `training_data_policy`, contamination and leakage gates enforce it.
- **Checkpoint selection** follows a rule written and committed *before* any checkpoint is scored
  (`docs/evaluation/CHECKPOINT_SELECTION_RULE.md`). Max-over-draws selection on the reporting population is the
  documented Study 001 defect. Sweep checkpoints with `scripts/evaluate_sft_checkpoints.py`.

## Methodology requirements (`docs/EVALUATION.md` §0)

- **Response-mode coverage:** an evaluation set detects only what it contains, so gates must cover ANSWER,
  TOOL_CALL, REFUSE and CLARIFY.
- **Wrong versus did-not-try:** report `accuracy`, `answer_rate` and `accuracy_given_answer` separately.
  `accuracy_given_answer` is `null`, not `0.0`, when nothing was attempted.
- **Truncation:** record `finish_reason` and truncation rate per stage. Uneven truncation invalidates a
  comparison, and residual truncation is reported as a truncation-adversarial interval.
- **Totals hide behaviour:** inspect failure modes, and never let a tiny suite carry a capability conclusion.
- **Scorer determinism:** seed stochastic dependencies in the wrapper, not in vendored checkers, and verify
  determinism by rescoring.
- **Same population:** every row of a comparison uses the same population (G9), with counts behind every rate.

## Benchmarks

- **Where they are defined:**
  - `registry/benchmarks.yaml`: pinned source, commit, evaluator version, `prohibit_training`;
  - `configs/benchmarks/`: one config per benchmark;
  - `configs/benchmark_suites/`: `smoke`, `tool_use_core`, `regression_core`, `agent_transfer`,
    `full_post_training`, `speculative_decoding`.
- **CLI:** `opengrad-benchmark list | validate | dry-run | run | compare | report | contamination-scan`. The same
  system is reachable as `opengrad benchmark …`, and `opengrad evaluate <target> --suite <suite> [--dry-run] --json`
  runs a suite on a checkpoint.
- **Adding one:** follow `docs/evaluation/ADDING_A_BENCHMARK.md` (register, config, `opengrad benchmark validate`,
  dry-run with `--limit 2`). For a backend, follow `docs/evaluation/ADDING_A_BACKEND.md`
  (`src/opengrad/benchmarks/backends/`).
- **Capability campaign** (IFEval, GSM8K, MMLU-Pro):
  - code: `src/opengrad/evaluation/capability.py` and `scripts/fetch_and_score_capability.py`;
  - `results/final_campaign_verdict.json` is regenerated by `scripts/build_final_verdict.py`, never edited;
  - the audit is `scripts/audit_campaign_final.py`.
- **Speculative decoding:** `docs/evaluation/SPECULATIVE_DECODING.md`. Quality must never be hidden by speedup.
  No speculative result exists yet, and native MTP drafting is gated on the component policy
  (`opengrad-training`).
- **Routing and quantized evaluation:** `src/opengrad/evaluation/routing.py`
  (`docs/evaluation/deployment-derived-routing.md`) and `src/opengrad/evaluation/quantized.py`.

## Contamination (Levels 1–5)

```bash
opengrad-contamination heldout-screen    # machine: levels 1-4; regenerated, never hand-edited
opengrad-contamination adjudicate        # human: level-5 verdicts in the audit file
opengrad-contamination quarantine        # derive the quarantine list from CONTAMINATED verdicts
```

The machine report and the human audit are separate files with separate owners
(`docs/evaluation/CONTAMINATION_ADJUDICATION.md`). Benchmark-level scans run through
`opengrad-benchmark contamination-scan --benchmark <id> --benchmark-data <jsonl> --training-data <jsonl>`
(`--record` writes the registry). Both scans use one engine, `src/opengrad/contamination/levels.py`; never
give a scan its own level logic. A scan never reports level 5 run and never reports a benchmark clean: the
benchmark adapters synthesize placeholder tasks, so a scan reads real data files and records their sha256
(`reports/ERRATA.md` §25).

## Failures and comparisons

- `opengrad failures <run_dir> --json` clusters failures into the taxonomy in
  `src/opengrad/benchmarks/taxonomy.py` (`src/opengrad/failures/analyzer.py`, `docs/FAILURE_ANALYSIS.md`).
- `opengrad compare <baseline> <candidate> --json` compares two evaluation directories. Report regressions beside
  gains (G10).

## Keeping this skill current

Update this skill in the same commit when a suite, held-out partition, selection rule, contamination artifact
or methodology requirement changes. Add a benchmark's special handling here only when it differs from
`ADDING_A_BENCHMARK.md`.
