# Public Sources for a Held-Out ANSWER Stratum: What Qualifies and What Must Be Built

> **Status:** source screening for Study 002's held-out `ANSWER` stratum, 2026-09-24. The study owner's
> decision is pending ([`registry/source_screening.yaml`](../../../registry/source_screening.yaml),
> `owner_decision`). This report is the written record of that screening; the per-candidate verdicts
> are in the screening log.
>
> **Where the numbers come from:**
> - the BFCL sizing (389, 95% range 274–600) is
>   [`bfcl-answer-sizing.json`](bfcl-answer-sizing.json), from the readings in
>   [`answer-sizing-readings.json`](answer-sizing-readings.json);
> - the overlap counts (40 exact, 49 half-contained, 62 flagged) are
>   [`bfcl-training-overlap.json`](bfcl-training-overlap.json).
>
> Both are regenerated by `scripts/audit_bfcl_answer_supply.py`. The sizing readings are one reader's
> judgement for sizing, not gold labels.

No public dataset available today can supply 601 clean, held-out ANSWER items on its own. The ANSWER case is a model that is offered tools, should answer in prose, and must not overlap OpenGrad's training sources. Most of the candidates hold **zero** items of that kind; the per-criterion counts are generated in [`docs/datasets/SOURCE_SCREENING.md`](../../../docs/datasets/SOURCE_SCREENING.md). They test tool calling, clarification or refusal, never a knowledge-answerable question placed next to irrelevant tools. Two published designs match the definition exactly, but neither can be used now: one is unreleased and the other is unlicensed. The one usable natural source is BFCL's relevance-detection data (Apache-2.0). It needs item-by-item re-adjudication, and a sample suggests it yields about 389 ANSWER items (95% range 274–600). So the recommendation has two parts. The natural stratum should be re-adjudicated BFCL irrelevance items. A second, constructed stratum should pair licence-clean knowledge questions with out-of-domain tool schemas, and it closes the gap to 601.

## 1. What a Held-Out ANSWER Item Must Satisfy

An item counts only if it satisfies all five conditions below:

- **Tools are offered.** A question with no tools tests plain chat, not the decision to abstain from calling.
- **No offered tool fits.** Either every tool is irrelevant, or a tool is related but unnecessary.
- **The question is answerable from general knowledge.** This condition separates ANSWER from UNSUPPORTED: a question that needs an absent tool (live data, private records, an action in the world) is UNSUPPORTED, not ANSWER.
- **The licence permits redistribution**, and there is a pinned revision.
- **The item is disjoint from the training sources.** Those are xLAM/APIGen-60k, Glaive v2, ToolACE, When2Call SFT, BUTTON and LoopTool-23k, plus the When2Call MCQ and LLM-judge test splits that are already in use.

Study 002's split specification sets three sizing targets and one screening rule:

- **Hard floor:** n ≥ 200 per mode.
- **10-point resolution:** n ≈ 385.
- **8-point resolution:** n ≈ 601.
- **Screening:** each ANSWER item must be checked against the training corpus by exact-text and near-duplicate fingerprints before use.

**Most irrelevance benchmarks fail the third condition.** They label every no-call item the same way, so a question the model can answer and a question no offered tool can serve both look like *don't call*. The *When Tools Get in the Way* authors make this criticism explicitly. BFCL "rewards declining irrelevant functions regardless of whether a direct answer was possible". They add that no existing benchmark supplies "a matched no-tool condition establishing that the question was answerable" [1]. A usable ANSWER stratum therefore needs a label that existing no-call datasets do not carry. Curation cannot be avoided, whatever the source.

## 2. BFCL Irrelevance, Live Irrelevance and Relevance Detection

- **Licence and revision.** BFCL is Apache-2.0 for both code and data [2][3]. OpenGrad's benchmark registry already pins GitHub revision `6ea5797`. At that revision, the relevance files hold **240** `irrelevance` items and **884** `live_irrelevance` items. The Hugging Face copy at `61fc060` holds 240 and 882. The 875 figure on older cards is stale; the v3 composition table confirms 882 live items [4][5].
- **Tools are always offered.** Every item carries one or more function schemas, and the gold behaviour is no call.
- **Provenance differs between the two files.** The non-live items were hand-built by the BFCL team [6]. The live items are naturally occurring "low-quality or irrelevant user queries" from Gorilla's hosted endpoint, left unmodified [7]. The worked examples in that write-up are UNSUPPORTED-shaped: a geocoding request offered only `multiply` and `add`.
- **Label quality is the main risk.** An independent audit found defects in 24 of 50 sampled BFCL v4 tasks. Two of the five irrelevance items it audited had *inverted* labels, where the offered tool was the correct call. An example is "What is the current time in Sydney, Australia?" offered `get_local_time` [8]. The project's own changelog also records repeated ground-truth fix rounds on irrelevance items [9].
- **How many are genuinely ANSWER.** A hand-read random sample (seed fixed; a sizing estimate, not gold) gives these shares:

| File | Sampled | Clearly ANSWER | Point estimate | 95% range |
|---|---|---|---|---|
| `irrelevance` | 50 | 35 (+4 borderline) | ~168 of 240 | 135–209 |
| `live_irrelevance` | 60 | 15 (+4 borderline) | ~221 of 884 | 139–391 |

- **Non-live file.** The knowledge-answerable items are mostly maths, history, how-to and definitions, e.g. a line slope, or who signed the Declaration of Independence. The rest need live or local data (nearest restaurant, bitcoin price) or are ambiguous.
- **Live file.** It is mostly UNSUPPORTED, CLARIFY and noise: sentence fragments, non-English shopping requests, API-key tasks, and at least one item where an offered `python_send_mail` actually fits. Its ANSWER items lean toward chit-chat (*hi*, *tell me a joke*).
- **Overlap with training sources.** The OpenGrad corpora were probed with a normalised exact match plus 8-gram containment of every BFCL question. 40 items match exactly and 49 are at least half-contained. The two sets overlap, and together they flag 62 items, about 5.5% of the total (7 of 240 `irrelevance`, 55 of 884 `live_irrelevance`):
  - Most sit in the When2Call MCQ and LLM-judge test sets, which were built from BFCL v2 Live [10].
  - A few sit in Glaive, xLAM and LoopTool: shared maths templates, and a Sydney local-time question.
  - BFCL's own deduplication covered only NexusRaven, Firefunctions, Anyscale and the NousResearch-Glaive set [7]. The rest of the screening is therefore OpenGrad's job.
- **Four-mode fit.** Good once relabelled. One pass assigns ANSWER, UNSUPPORTED, CLARIFY or CALL (the last catches inverted labels), and the non-ANSWER items become useful UNSUPPORTED and CLARIFY supply.
- **Excluded categories.** The 200-item `chatting` category offers **no tools** [3], so it fails condition one. The 18 `live_relevance` items are CALL items.

## 3. When2Call Splits Beyond SFT, MCQ and LLM-Judge

When2Call is disqualified on two independent grounds.

- **No ANSWER items by design.** The paper's split table shows **zero** direct-answer gold items in every split: test, LLM-judge, SFT and preference. The paper states the dataset "is constructed to assume that the direct answer is always a hallucination and, thus, always wrong" [10].
- **Shared upstream.** The training splits were generated from `Salesforce/xlam-function-calling-60k`, the exact dataset OpenGrad trains on [11]. The preference split (9,000 rows) shares that upstream. The test split was built from BFCL v2 Live.

CC BY 4.0 and a pinned revision (`0582f77`) exist [12], but neither matters when the count is zero. This also explains why OpenGrad's frozen held-out set, which comes from When2Call's test split, carries no ANSWER items.

## 4. API-Bank

API-Bank is MIT-licensed [13], with 1,888 training and 314 evaluation dialogues. It contributes **0** ANSWER items. Its three ability categories, Call, Retrieve+Call and Plan+Retrieve+Call, partition the whole benchmark. *No API call* appears only as a model *error type*, never as gold [14][15].

## 5. ToolBench and StableToolBench

Both are Apache-2.0 repositories whose data comes from RapidAPI, so the RapidAPI terms of service apply. ToolBench's 126k instances are pure CALL data [16]. StableToolBench's solvability filter concerns whether a task *can* be completed, not whether a tool is needed [17]. Both contribute **0** ANSWER items.

## 6. NESTFUL

NESTFUL is Apache-2.0 with 1,861 items, all executable nested call sequences built from MathQA and StarCoder2-Instruct [18][19]. It contributes **0** ANSWER items. One warning for any other use: the superseded `data_v1` draws on Glaive, so only v2 may be pinned [20].

## 7. tau-bench

tau-bench is MIT with 165 multi-turn tasks: 115 retail and 50 airline. Each is graded by whether the final database state matches an annotated goal. Instructions were also rewritten to remove any path that avoids the tool call [21][22]. It contributes **0** ANSWER items and fits single-prompt scoring poorly.

## 8. ToolSandbox

ToolSandbox ships under a custom Apple licence that permits use and redistribution. It is not an OSI or Creative Commons licence, so the text must be quoted rather than named [23]. Its Insufficient Information scenarios withhold a *needed* tool or argument. The authors contrast them with BFCL, where "tools are often irrelevant", while theirs involve "highly relevant tools" [24]. That is UNSUPPORTED, in a multi-turn format, so ToolSandbox contributes **0** ANSWER items.

## 9. Hammer Irrelevance Data and xLAM-Irrelevance

`xlam-irrelevance-7.5k` is CC-BY-4.0 at `34323bf`. It was built by sampling 7,500 items from `xlam-function-calling-60k` and deleting the ground-truth tool [25][26]. **Barred:** every prompt is an OpenGrad training prompt. The items are also mostly UNSUPPORTED-shaped, because the question still needs the removed tool. The Hammer code is Apache-2.0, a different licence from the data [27]. HammerBench's irrelevant items expect a fixed refusal string, "Sorry, no tool is suitable for your request", which is again UNSUPPORTED [28].

## 10. MMAU

MMAU's tool-use portion is built from RapidAPI functions, and its DAG-QA items are multiple-choice plan selection [29][30]. It contributes **0** ANSWER items. Its dataset licence could not be confirmed because the dataset card would not load, but the count makes that moot.

## 11. T-Eval

T-Eval is Apache-2.0. It decomposes tool use into six sub-skills over ToolBench's RapidAPI tools, and every item exercises a tool step [31][32]. It contributes **0** ANSWER items.

## 12. Seal-Tools

Seal-Tools is Apache-2.0 with 14,076 self-instruct instances, all of which call tools [33][34]. It contributes **0** ANSWER items.

## 13. ToolAlpaca

ToolAlpaca is Apache-2.0 with 3.9k instances over public-apis APIs. Every instance contains an action step [35]. It contributes **0** ANSWER items.

## 14. NoisyToolBench

NoisyToolBench is Apache-2.0 with 200 items derived from ToolBench [36]. Each item is a clear instruction corrupted by missing information, ambiguity, errors or beyond-capability requests. The gold behaviour is a clarifying question, or for beyond-capability items, "telling the user that the query is beyond the capabilities" [37]. So the items are CLARIFY and UNSUPPORTED, with **0** ANSWER.

## 15. RoTBench

RoTBench is Apache-2.0 and measures tool-use robustness under five noise levels, with queries from ToolEyes [38][39]. It contributes **0** ANSWER items.

## 16. ToolHop

ToolHop has CC BY 4.0 data and Apache-2.0 code, with 995 multi-hop queries built from MoreHopQA [40]. Its *direct* condition is a prompting setup applied to every item, not a per-item label. Tools raise accuracy substantially, which indicates most items need them [41]. It contributes **0** labelled ANSWER items. Its questions could serve as raw material only after a new tool-necessity annotation.

## 17. Other Candidates

- **ACEBench.** Its *special* category, where the function ability is exceeded, means no candidate function can resolve the request. That is UNSUPPORTED, and nothing requires the question to be knowledge-answerable [42].
  - The repository is MIT, but its LICENSE names Microsoft as copyright holder, which looks like an uncustomised template [43][44].
  - OpenGrad's benchmark registry records ACEBench as Apache-2.0 at a ServiceNow URL. That mismatch should be checked separately.
- **ToolBeHonest** is MIT for data and code, pinned at `22da253`, with 350 unsolvable items, every one built by removing a genuinely needed tool [45][46]. It contributes no ANSWER items. It is, however, the cleanest external supply found for an UNSUPPORTED set. Even so, its 350 items fall short of the 385 that the unanswerable-question population needs.
- **When2Tool** is the closest *existing* data. It has 3,780 rows, and its *easy* tier (750 test and 300 train items across 15 environments) is designed to be solvable without the offered tool, e.g. `20+20` with a calculator offered [47]. Three problems block it:
  - there is **no licence** on the card or in the repository, so by default it cannot be redistributed [48];
  - its tool-necessity label is computed per model at evaluation time, not shipped as gold;
  - its items test *unnecessary* tools, not *irrelevant* ones, a narrower slice of ANSWER.
- **When Tools Get in the Way** is the ideal design. It pairs 500 closed-domain questions with topically adjacent but unnecessary tools, plus a matched no-tool control. Answer rates fall from 98.2% to 63.5% when the tool appears [1]. The data is **not released**: "We will release the data and evaluation code on acceptance." A related study reports that models largely *know* when they need a tool but act on it poorly [49].
- **ToolQA** has only tool-required questions [50].
- **Question sources for a constructed set:**
  - **Natural Questions** is CC-BY 4.0. Its public dev split holds 7,830 five-way-annotated questions, of which about 36% have a short answer, roughly 2,800 [51].
  - **SimpleQA** is MIT with 4,326 questions, but it was adversarially selected to make strong models hallucinate, so it is weak for *answerable from knowledge* [52][53].
  - **TriviaQA**'s repository is Apache-2.0. However, its maintainers state that the university "does not own the copyright of the questions", so redistribution is uncertain [54][55].

## 19. Recommendation: Best 1-3 Sources and the Curation They Need

**1. BFCL `irrelevance` + `live_irrelevance`, re-adjudicated. This is the natural stratum.** It is the only released, permissively licensed source of real tools-offered, no-call prompts, and it is already pinned in OpenGrad's registry.

- **Curation:**
  - Draw both files at `6ea5797`.
  - Remove every item that collides with a training corpus or with the When2Call test set. Run the repository's contamination engine at all four automated levels, not only the exact and 8-gram probe used here.
  - Relabel each item into CALL / ANSWER / CLARIFY / UNSUPPORTED under the existing model-annotation protocol. That protocol uses three non-Claude models and two-of-three agreement, and sends disagreements to adjudication. An ANSWER label must also carry a rationale that the question is answerable without any tool.
  - Record the language of each item, and report English-only counts alongside the total.
- **Expected yield:** about 389 ANSWER items (95% range 274–600). That clears the 200 floor and probably the 385 needed to resolve 10 points, but not 601. The same pass also yields several hundred UNSUPPORTED and CLARIFY items, which the other strata can use.

**2. A constructed ANSWER set from Natural Questions dev short-answer questions with out-of-domain tool schemas. This closes the gap to 601 and more.** The design copies what *When Tools Get in the Way* shows is missing from BFCL: a matched control proving each question is answerable.

- **Curation:**
  - Sample questions with a short answer.
  - Attach one to three tool schemas drawn from BFCL function documentation (Apache-2.0). The schemas must be chosen so that none could plausibly serve the question. That means never a search, lookup or retrieval tool, since a searchable question plus a search tool makes CALL correct.
  - Run a no-tool control to confirm the question gets a direct answer.
  - Fingerprint-screen the result against every training corpus.
- **Reporting.** Keep it as a separate labelled stratum (`ANSWER-constructed`) next to `ANSWER-natural`, because a synthetic pairing measures a different distribution from real user traffic.
- **Licence.** CC-BY 4.0 requires attribution.

**3. Watch-list rather than now:**

- *When Tools Get in the Way*, once its data is released: re-check the licence and screen it.
- When2Tool, if its authors add a licence: ask them. It would then add about 750 test items of the unnecessary-tool kind.

**What would change this recommendation:**

- If a full relabel of BFCL finds far fewer ANSWER items than the sample suggests, for example under 200, the constructed set becomes the primary stratum rather than the complement.
- If the unreleased 500-pair set appears under a permissive licence, it should replace the constructed set. It was built and validated for exactly this measurement.
